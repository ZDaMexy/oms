Map of the BMS default visual geometry knobs (last touched 2026-06-20). All are **visual/geometry only** — none affect judgement/scoring/scroll timing.

**THE normalization landmine (lane width):** physical lane width = `lane.RelativeWidth / TotalRelativeWidth × PlayfieldWidth × screenWidth` (`BmsPlayfield.applyLaneBounds`). Lanes are **normalized to fill** `playfieldContainer`, so scaling all `*LaneRelativeWidth` proportionally does **NOTHING** (numerator and denominator both scale → cancels). Only two things matter:
- the **ratio** between lanes (e.g. scratch:key) — set via `ScratchLaneRelativeWidth` vs `NormalLaneRelativeWidth`;
- the **physical total width** — the ONLY lever is `PlayfieldWidth` (in `BmsPlayfieldLayoutProfile.CreateDefault`). Notes fill lane width (`DrawableBmsHitObject`: `RelativeSizeAxes.X, Width=1`) so they auto-scale with the lane.

**The `BmsRulesetSetting.PlayfieldWidth` config is IGNORED** — strict profile (Playfield Scale/Offset were removed). `TestSceneBmsPlayfieldLayoutConfig` asserts the config does NOT override the profile. To change geometry, edit the **profile `CreateDefault` defaults**, not config.

**Knob map (`osu.Game.Rulesets.Bms/UI/`):**
- Lane/note width → `BmsPlayfieldLayoutProfile.CreateDefault` `playfieldWidth` default. Currently `Math.Clamp(laneCount*0.06f, 0.35f, 0.8f) * 0.825f` (orig ×0.75 −25%, then ×1.1).
- Scratch:key width ratio → `ScratchLaneRelativeWidth` / `NormalLaneRelativeWidth`. Currently `1.5f` / `1f` (scratch 1.5× key).
- Note thickness (bar height) → `DrawableBmsHitObject` ctor `Height = hitObject is BmsHoldNote ? 28 : 22.5f` (22.5 = regular note + LN head/tail caps; the `28` is a non-duration fallback overridden by the scrolling container to the hold length — NOT a visible thickness).
- LN body width → `DefaultBmsLongNoteBodyDisplay.Width` (`0.5775f` as of 2026-06-21, relative to lane; was 0.525, ×1.1; translucent stripe spanning the full hold).
- **LN body colour + 3-state gameplay visual (2026-06-21, P1-A):** body colour now MATCHES THE HEAD (`GetLongNoteHead` = full note colour, alpha `0.8`) instead of the old darkened `GetLongNoteBody` stripe. The body reacts to play via a **skin-agnostic** bindable: `DrawableBmsHoldNote` exposes `IBindable<BmsLongNoteBodyState> BodyState` (enum `Idle/Holding/Broken` = unactivated/activated/missed), set each `Update()` **purely derived** from `isHolding`+head/tail judged (isHolding→Holding; head unjudged→Idle; head&tail both IsHit success→Holding; else→Broken). `DefaultBmsLongNoteBodyDisplay` `[Resolved] DrawableHitObject`→cast `DrawableBmsHoldNote`→`bodyState.BindTo(holdNote.BodyState)` (field typed `IBindable<>` so `.BindTo` uses the interface overload — same as mania `DefaultBodyPiece`; `DrawableHitObject` is `[Cached]`, body resolves parent through the `SkinnableDrawable`). Default mapping: **Idle==Holding** (head colour+0.8) / **Broken = grey+dim** (`BmsDefaultPlayfieldPalette.GetLongNoteBodyBroken` = blend toward luminance 0.85 + dim 0.45, alpha `0.32`), 80ms fade. No parent (skin fallback queries) → stays Idle. **Broken→recover is HCN-ONLY** (LN/CN broken holds stay broken till fade; only HCN re-grab flips isHolding back true → Holding) — tied to the P1-E `AllowsRegrabAfterRelease()` correction, see [[reference_bms_judgement_parity]]/P1-E. Head/tail untouched (tail still `Alpha=0`).
- LN tail cap → `DefaultBmsLongNoteTailDisplay` set `Alpha = 0` (removed by default; the body stripe already spans the full hold up to release, so no gap; tail JUDGEMENT object is unaffected — visual only). `BmsNoteSkinElements.LongNoteTail` lookup + `GetLongNoteTail` colour kept so skins can still override.
- Playfield vertical → `playfieldContainer` is **top-anchored at the screen edge** (`Y=0`; `BmsPlayfield`: initial + all three `applyPlayfieldStyle` cases use `Top*` with `RelativePositionAxes=Axes.X` only). Height = public const `BmsPlayfieldLayoutProfile.DEFAULT_PLAYFIELD_HEIGHT` (`0.92f` as of 2026-06-20; was 0.86 briefly, 0.95 originally). Judgement line at `0.92` screen height, gauge flush below (`gauge_top = DEFAULT_PLAYFIELD_HEIGHT + 0.002`). **The earlier `PLAYFIELD_VERTICAL_OFFSET` (shifted the whole column down) was REMOVED 2026-06-20** — the user wants the top flush to the screen edge (notes appear at the very top, matching green-number semantics); to put the gauge lower, RAISE `DEFAULT_PLAYFIELD_HEIGHT` (keeps top at edge, judgement line drops), do NOT re-add a downward offset. **GN is independent of playfield height** (GN = visible time = `TimeRange`; with `HitTargetVerticalOffset=0` the `scrollLengthRatio≡1` so `TimeRange` is unaffected — height only changes pixel sweep distance, not reaction time), so changing height is safe for the green-number contract.
- Hit target sits at the **bottom of the lane** (`BmsHitObjectArea`, `HitTargetVerticalOffset=0`, BottomLeft anchored).
- **Gauge placement + integration (2026-06-20, P1-A E1):** the gauge (`BmsGaugeBar`) is an **integrated band that reads as the playfield column's bottom segment**, sitting **just below the judgement line**, **width-matched to the lane strip** and **mirroring P1/P2/centre side anchoring**. Visual (groove-gauge, integrated per user feedback): single flush band height 34, **no surrounding border** (only a 1px gauge-accent `topAccent` hairline at the top), navy background gradient `BmsDefaultHudPalette.GaugeTrackTop(26,32,48)→GaugeTrackBottom(13,19,31)` matching the playfield lane/baseplate navy, 10 faint segment ticks, and `NORMAL` label (centre-left) + `%` value (centre-right, size 20, shadowed) **overlaid on the bar** (no separate header row). It STAYS in the HUD `IBmsHudLayoutDisplay.SetComponents(wrappedHud, gauge, combo)` contract (**signature NOT changed** — `TECHNICAL_CONSTRAINTS` HUD host rule 1 forbids it). `DefaultBmsHudLayoutDisplay` makes it geometry-aware by resolving `PlayfieldWidth`/keymode from `[Resolved(CanBeNull)] GameplayState` (`BmsLaneLayout.CreateFor`) and `PlayfieldStyle` from game-global `IRulesetConfigCache.GetConfigFor(new BmsRuleset())` (same `BmsRulesetConfigManager` instance the playfield uses — bind for live changes). Sets gauge `RelativeSizeAxes.X + Width=PlayfieldWidth`, `RelativePositionAxes.Both + Y=PlayfieldHeight+0.002` (tight flush gap), Anchor/Origin/X per `PlayfieldStyle.GetAppliedStyle(keymode)` reusing public `BmsPlayfield.SIDE_ANCHORED_HORIZONTAL_INSET` (0.05). No `GameplayState`/config (skin editor preview / isolated tests) → graceful centre + fallback width 0.4. Why-in-HUD-not-Overlays: `HealthDisplay.HealthProcessor` is non-null `[Resolved]` (throws if absent) and `BmsPlayfield` is instantiated bare in many tests → mounting in playfield/Overlays needs a HealthProcessor guard; keeping it in HUD (gameplay-only) + the frozen `SetComponents` contract is cleaner.
- **Combo placement (2026-06-20):** `BmsComboCounter` is positioned by `DefaultBmsHudLayoutDisplay.applyComboPlacement()` at the **playfield centre** (intersection of the playfield width/height midlines): horizontal centre per `PlayfieldStyle.GetAppliedStyle(keymode)` (reusing the same `PlayfieldWidth` + `SIDE_ANCHORED_HORIZONTAL_INSET` as the gauge), vertical = `DEFAULT_PLAYFIELD_HEIGHT/2`; `Anchor=TopLeft, Origin=Centre, RelativePositionAxes=Both`, re-applied on PlayfieldStyle change. `BmsComboCounter` had its background colour-block (the `body` container: gradient `background` + `glow` + `accentStrip` + rounded border) REMOVED per user — now just a centred `COMBO` label + count number (pulse/flash on the number, shadowed). Regression: `TestComboCentredOnPlayfield`.
- **Gauge hidden by ShowHealthBar / NoFail landmine (2026-06-20, P1-A — cost a long debug):** `BmsGaugeBar : HealthDisplay`, and `HealthDisplay.LoadComplete` binds itself to `[Resolved] HUDOverlay.ShowHealthBar` and `this.FadeTo(0)` when it's false. Anything that sets `ShowHealthBar=false` (NoFail / a generic "hide health bar" toggle) silently fades the BMS groove gauge to invisible — combo unaffected, so symptom is "combo shows, gauge gone". **Diagnostic blind spot that hid this:** gauge tests using a bare `DependencyProvidingContainer` resolve `hudOverlay`→null → `showHealthBar` stays true → gauge always visible → masks the fade path; you MUST use a REAL `HUDOverlay` (e.g. load a real `BmsSoloPlayer` and set `ShowHealthBar.Value=false`) to reproduce. **Fix:** `BmsGaugeBar` resolves `[Resolved(CanBeNull)] HUDOverlay` and in `LoadComplete` subscribes to `ShowHealthBar` re-asserting `FinishTransforms()+Alpha=1` (registered AFTER base → bound-copy subscribers fire before own subscribers → it wins) so the groove gauge is immune (core gameplay info, always shown); HUD-wide `ShowHud` fade still works via the parent. Regression: `TestGaugeBarStaysVisibleWhenHealthBarHidden` in `TestSceneBmsSoloPlayerPreStart`. Note the strip (combo/leaderboard removal) was NOT the cause — that was ruled out first.
- **BMS gameplay: remove default combo + leaderboard from the skin CONFIG, not hide (2026-06-20, P1-A):** the bottom-left default combo AND the left gameplay leaderboard are **same-source** — upstream `LegacySkin.GetDrawableComponent` ruleset-`MainHUDComponents` default layout literally does `new LegacyDefaultComboCounter()` + `new DrawableGameplayLeaderboard()` (osu.Game/Skinning/LegacySkin.cs ~420/422); `BmsSkinTransformer` packs that as the BMS HUD's wrapped layer. Fix = **strip them from the config tree at assembly time**: `BmsSkinTransformer.stripDefaultHudElements(wrappedHud)` does `Container.Remove(child, true)` for every `ComboCounter` / **`LegacyDefaultComboCounter`** / `DrawableGameplayLeaderboard` in the wrapped container's direct children — so they never enter the BMS HUD tree (no render, no skin-editor serialisation, no first-frame flicker). The BMS combo (`BmsComboCounter`) is added separately by `SetComponents` and is NOT in the wrapped layer, so removing all wrapped combos is safe; the global (Ruleset==null) layer's score etc. are untouched. **LANDMINE (cost a wrong iteration):** the upstream default combo is `LegacyDefaultComboCounter : CompositeDrawable, ISerialisableDrawable` — it is **NOT a `ComboCounter`**, so matching only `ComboCounter` strips the leaderboard but leaves the combo. Strip AND its regression test must use the real `LegacyDefaultComboCounter` type (a `: ComboCounter` test dummy false-passes). User explicitly wanted "removed from config, NOT hidden" → do NOT use `Alpha=0` / `Configuration.ShowLeaderboard=false` (those were tried and reverted). `DefaultBmsHudLayoutDisplay` still has a one-shot hide loop as a stray-combo safety net. Regression: `TestRulesetHudStripsDefaultComboAndLeaderboard` in `BmsSkinTransformerTest`.

**Tests pin these exact values** — change a value → update assertions in `BmsLaneLayoutTest`, `TestSceneBmsPlayfieldLayoutConfig` (incl. measured scratch:key ratio, lane-height fraction `0.92`, `PlayfieldHeight 0.92`), `BmsSkinTransformerTest` (LN body width `0.5775` + colour = head colour `YellowKeyNote`/`ScratchNote` + alpha `0.8`; also "HUD includes gauge" presence — gauge still a HUD child). LN body 3-state lifecycle (incl. HCN recover) → `BmsDrawableRulesetTest.TestBodyStateFollowsHcnHoldLifecycleWithRecovery` + `ComputeBodyStateForTesting()` asserts in the CN tests. Gauge placement contract → `TestSceneBmsHudGaugePlacement` (width=PlayfieldWidth / below judgement line / centre / P1 side-anchor mirror, caches a `GameplayState` via `DependencyProvidingContainer` + uses `OsuTestScene.RulesetConfigs`).
