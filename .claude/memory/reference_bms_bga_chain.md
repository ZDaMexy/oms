BMS BGA（背景图/背景动画）链路。归 **P1-L Phase 5/5.1/5.2**（演出视觉复刻；**落地 2026-06-14（Phase 5）/ 2026-06-15（Phase 5.1 老式视频转码）/ 2026-06-23（Phase 5.2 开局即播+会话级缓存+ultrafast+扫描线加载进度）**，自动化通过 BMS 954/954 + Release 0 错，实机人工视觉验收待办）。此前文档把 BGA 视频/动画标为 mainline Phase 2 future-scope，本次激活并归入 P1-L。

**实现期发现的坑（关键）**：① `BmsBeatmapConverter.buildEventTimeline` 的 `register(...)` 此前**漏注册 BGA 事件时刻** → BGA 的 measure/fraction 不会进 `eventTimes`、`buildBgaTimeline` 的 `TryGetValue` 全 miss；修复＝补 `register(decodedChart.BgaEvents...)`（与 mine/invisible 并列）。② 视频时钟同步依赖 `DrawableRuleset.Overlays` 在 `FrameStabilityContainer` 内（已确认 line 177-189）→ 浮窗 `Time.Current` = frame-stable 游玩时间，`PlaybackPosition = Time.Current - entry.StartTime` 正确、seek/retry 安全。③ BMS 恒 filesystem-backed（`FilesystemStoragePath` 非空）→ `WorkingBeatmap.GetStream(assetFile)` 直接按相对名从谱面文件夹解析（不像 storyboard 走 realm hash store）；播放器用自建 `TextureStore`（backing `WorkingBeatmapFileStore` 委托 `GetStream`）取图片、`GetStream` 取视频流。

**现状缺口（审查结论）**：解析层（P1-K）已完整忠实产出 `BmsDecodedChart.BgaEvents`（通道 `04`base/`06`poor/`07`layer/`0A`layer2）+ `#BGA/#@BGA/#ARGB/#SWBGA/#POORBGA` typed 定义 + `BitmapTable`。但 **`BmsBeatmapConverter` 只取一个静态 `metadata.BackgroundFile`（`GetPreferredBackgroundAssetReference()`），整条 BGA 时间线被丢弃**——`BmsBeatmap` 此前无 BGA 字段。显示层 `BmsBackgroundLayer`（`StaticBackgroundLayer` skin lookup）是静态占位件 + 元数据标签，且挂在 `BmsPlayfield.playfieldContainer` 内、位于不透明 lane 背板（`DefaultBmsLaneBackgroundDisplay : Box`）**之下 → 游玩时完全被遮挡**（14K DP 时塌进两 playfield 中缝、连 "STAGEFILE/BACKBMP/..." 标签都露出来）。玩家实际只看到全屏 `BackgroundScreenBeatmap`。

**冻结产品决策（用户拍板）**：① 图序列 + 视频一起做；② 默认布局**镜像 playfield 侧、放到屏幕角落**（`BmsBgaPlacement` 枚举 = `TopLeft/TopRight/BottomLeft/BottomRight/Center`；5/7/9K 单角：P1→`TopRight` / P2→`TopLeft` / 居中→`TopRight`；**14K DP→屏幕四角各 mount 一个 BGA**——2026-06-20 由原"两 playfield 中缝(Center)"改成四角，因中缝压游玩区/combo；`DefaultBmsBgaPanelDisplay` 重构为 `framesContainer` + 每角一个 `BmsBgaPlayer`，14K 用更小 `corner_14k_size`(0.13×0.16) 贴窄双打边距、`NotifyMiss` 转发全部 player。**坑**：keymode 必须用 `[Resolved] GameplayState` + `BmsLaneLayout.CreateFor` 解析（曾用 `WorkingBeatmap.Beatmap as BmsBeatmap` 检测失败→退回大尺寸遮挡 playfield）；**代价**：14K 四 player 对视频 BGA = 4 解码器，图片廉价。回归 `TestSceneBmsBgaPanelLayout`）；③ 等比完整 + 黑边（letterbox，`FillMode.Fit`），毛玻璃填充留后续皮肤可选；④ "浮窗" = 游戏内皮肤可定制覆盖控件（**非** OS 窗口）；⑤ 仅 native BMS ruleset 路径，converted-mania（Mania ruleset 下、无 `BmsPlayfield`/`Overlays`）不在 v1。

**实机验收后微调（2026-06-14，用户确认视频 BGA 播放 ✅）**：① 全屏背景——`DefaultBmsPlayfieldBackdropDisplay`（playfield `Backdrop` skin 元素）此前是覆盖全屏的不透明深色 Box，把谱面背景完全挡黑（游玩时全局背景 `BlurAmount=0` 也被它盖住）；改为渲染谱面背景的**模糊（sigma≈20，半分辨率 `BufferedContainer`+`FrameBufferScale 0.5`，同 song-select `SongSelect.cs` 的 blur 20）+ 黑 0.4 暗化**铺满整个背景面，play strip 与 BGA 浮窗仍在其上，无背景回退原 Box。② BGA 浮窗默认缩到 ~75% + 顶角锚（右→右上 / 左→左上 / 中→顶中），避开 playfield 与顶部 gauge/combo。

**视频解码坑（关键，2026-06-14 修）**：osu!framework `Video(Stream)` 的 .NET-Stream AVIO 打不开**老式 MPEG-1 program-stream `.mpg`**——`VideoDecoder.prepareDecoding()` 在 `avformat_open_input` 阶段 `AVERROR_INVALIDDATA`（runtime 日志 "VideoDecoder faulted: Error opening file or stream: Invalid data found (-1094995529)"）→ BGA 全黑。**这是框架/FFmpeg 层限制，不是 BMS 链路问题**（事件正确建立）。修法：`BmsBgaPlayer.createVideo` **优先按绝对文件路径** `new Video(path,…)`（BMS 恒文件系统直读 → external 用绝对 `BeatmapSetInfo.FilesystemStoragePath`、internal 用 `Storage.GetFullPath(相对)`），无路径回退 stream；仍 `Video.IsFaulted` 时 base 层回退 STAGEFILE 静态图（不黑屏）、overlay/poor 隐藏。**实测结论（2026-06-14，用户复测）：filename 路径对该 `.mpg` 仍 `INVALIDDATA`**——框架捆绑 FFmpeg（avformat-58/4.x）视频管线对老式 MPEG-1 program-stream 的打开/探测就失败（文件头 `00 00 01 BA` 合法、beatoraja 能播），**非 BMS 侧可修**（要改框架 `VideoDecoder` 探测/probesize，fork 级）；真正生效的是静态图回退，老 `.mpg` 显示 STAGEFILE。`.mp4`/H.264 一直正常。**Phase 5.1（2026-06-15）已做"真播老视频"**：`BmsBgaVideoCache`（opt-in `BgaVideoTranscode`，默认开）用**外部 ffmpeg**（用户自备：PATH `ffmpeg` 或放 `ffmpeg.exe` 进数据目录；OMS 不分发）把老式扩展名（`.mpg/.mpeg/.avi/.wmv/.flv/.m1v/.m2v/.mkv`）转 H.264 `.mp4` 缓存到 `<dataRoot>/bga-video-cache/`（键 `SHA1(源路径|size|mtime)`，先 .tmp 后原子改名），命令 `ffmpeg -y -hide_banner -i <src> -an -c:v <enc> -pix_fmt yuv420p -movflags +faststart`（**2026-06-22 起 `<enc>` 先 libx264、失败再回退内置 mpeg4**——见下「转码健壮性」）；`BmsBgaPlayer` 预热转码 + Pending 节流 1s 重试 + 本场热替换换入；无 ffmpeg/关闭/失败＝静态图回退（无回归），友好格式 `.mp4/.m4v/.mov/.webm` 直开不转。转码 runner 可注入便于单测（`BmsBgaVideoCacheTest`）。缓存无大小上限是已知后续项。诊断法：查 `<dataRoot>/logs/*.runtime.log`（数据根可能被 `%APPDATA%/oms/storage.ini` 的 `FullPath` 重定向，如 `D:\oms\data`）grep `VideoDecoder|ffmpeg|INVALIDDATA`。**设置 UI 改版（2026-06-22）**：该开关在 `BmsSettingsSubsection` 改名「ffmpeg完整BGA支持」、描述精简「对老式BGA提供转码播放支持，需自行放置ffmpeg到数据目录」（config 键 `BgaVideoTranscode` 不变，纯展示层）；新增两按钮——「检测 ffmpeg 安装状态」走新 public static `BmsBgaVideoCache.FindAvailableFfmpeg(IReadOnlyList<string>? candidates)`（**镜像运行时 `resolveFfmpeg` 顺序**：候选文件存在性→扫 PATH 下 `ffmpeg.exe`/`ffmpeg`，返回路径或 null；候选＝`storage.GetFullPath("ffmpeg.exe")`+`AppContext.BaseDirectory/ffmpeg.exe`，与 `BmsBgaPlayer.setUpVideoCache` 一致）结果写状态行；「打开 ffmpeg 安装目录」＝`host.OpenFileExternally(storage.GetFullPath(string.Empty)+Path.DirectorySeparatorChar)` 开数据目录根。`BmsSettingsSubsection` 新 `[Resolved] Storage`/`[Resolved] GameHost`。**转码健壮性（2026-06-22 跟进，用户反馈「ffmpeg 已检测到但 .mpg 仍静态」）**：症状链＝转码失败→`Resolve` 返回 `Unavailable`→直开 .mpg faulted→静态；且失败近乎无声（**stderr 被读后丢弃、仅 Debug 记一句**）。**确诊真因（实机日志，先做诊断改造才看见）＝转码输出写到 `<hash>.mp4.tmp`，ffmpeg 按文件扩展名推断输出容器、`.tmp` 不是已知格式 → 选不出 muxer：`Unable to choose an output format for '...mp4.tmp'; ... Error initializing the muxer ... Invalid argument`。libx264 一直可用**（错误在输入分析之后的 muxer 阶段，libx264 与回退 mpeg4 报同一错，证实是容器/扩展名非编码器——当初「缺 libx264」是错误假设）。**真修＝转码命令加 `-f mp4` 显式指定 muxer**（`BmsBgaVideoCache.BuildTranscodeArguments` 抽出可测，args＝`-y -hide_banner -i <src> -an -c:v <enc> -pix_fmt yuv420p -movflags +faststart -f mp4 <dst.tmp>`）。配套三处治理（其中①②是定位真因的前提）：① **编码器回退**＝`runFfmpeg` 拆 `runFfmpegWithEncoder`，先 libx264、失败（且非 ffmpegMissing）再**内置恒有的 mpeg4**——**关键认知：框架打不开的是老式容器（MPEG-1 PS）不是编码器，转干净 .mp4 后任一可解码编码器都行**，故缺 libx264 也能转；② **失败可见**＝并发读 stdout/stderr（防满缓冲死锁）+ 把 ffmpeg 输出记日志（这是定位 `.tmp` muxer 真因的关键，原本静默吞掉）；**降噪**＝每编码器完整 stderr 记 `Verbose`（文件、不刷通知），`startTranscode` 每失败源只发**一条 `Important`** 摘要（`failedDestinations.TryAdd` 去重，重试不重复弹——曾因每编码器每重试都 Important 致通知刷屏）；③ **检测真实化**（回应「只查文件存在」疑点）＝新 `BmsBgaVideoCache.ProbeFfmpeg(candidates)` **真跑** `ffmpeg -hide_banner -encoders`、查 `libx264` 子串，返回 `NotFound/NotExecutable/ReadyWithoutH264/Ready`；「检测」按钮改走它（后台 `Task.Run`+`Schedule` 回填，`GetResultSafely` 避 `Task.Result` 禁用 API）。`FindAvailableFfmpeg`（候选→PATH，纯存在性）保留供 Probe 内部用。回归 `BmsBgaVideoCacheTest` +2（候选解析确定性 + `TestTranscodeArgumentsSpecifyMp4MuxerForTmpOutput` 断言 args 含 `-f mp4`）；编码器回退/Probe/真实转码走真实进程不在注入式单测内（注入 runner 用例不回归），BMS 947/947。**教训**：BGA 转码失败先做诊断改造（surface stderr）再下结论——「缺 libx264」假设错了，真因是 `.tmp` 输出扩展名让 ffmpeg 选不出 muxer，`-f mp4` 一行解决。

**第二个真因（`-f mp4` 后转码成功但视频全黑 + runtime 暴涨 3614 行，实机日志确诊）＝产出的 H.264 mp4 框架内置 FFmpeg 解不了**：D3D11VA 硬解 `Failed to send avcodec packet: Invalid data found (-1094995529)` → `Disabling hardware decoding` → 软解回退**仍每包失败** → 0 帧黑；每失败包记一行（**3360/3614 行刷屏**，Verbose、仅日志无通知）。框架能放普通 H.264 mp4（2026-06-14 已验），故是**外部 ffmpeg 产出码流对框架老版 FFmpeg/硬解路径不兼容**（libx264 默认 High profile 在独立播放器正常、框架内每包失败）。**修＝转码约束最广兼容 H.264**：`BuildTranscodeArguments` 对 libx264 加 `-profile:v baseline`（无 B 帧/无 CABAC，HW 与老 SW 都稳解；mpeg4 回退无此档不加）、`-vf setpts=PTS-STARTPTS,setsar=1`（清老 .mpg ~0.44s 起始偏移避免 edit list + 方形像素）、`-map 0:v:0`（仅视频流）。**关键坑：旧不可解码 .mp4 已缓存**——`Resolve` 命中 `File.Exists(destination)` 直接返回旧坏文件不重转，故 `cacheKey` 加 `transcode_version`（=2，随转码参数变更 bump）失效旧缓存自动重转（旧文件成孤儿、可删 `bga-video-cache/`）。回归 +`TestTranscodeArgumentsOmitH264ProfileForMpeg4Fallback` + 扩 mp4-muxer 测断言 baseline。

**第三次实机：baseline 仍解不了（每包 Invalid data）+ runtime 47948 行刷屏——确认不是 profile 问题**。High/baseline 都失败 → 框架内置 FFmpeg/硬解路径对**外部 ffmpeg 转码产物**不兼容（框架能放普通 .mp4=2026-06-14 已验；区别是这些由用户外部 ffmpeg 产出）。**关键 API 限制**：osu.Framework `Video` 仅 `Video(string)/Video(Stream)` 两 ctor，`TargetHardwareVideoDecoders` 在内部 `VideoDecoder`、**无法按视频强制软解**，只有全局 `FrameworkSetting.HardwareVideoDecoder`（设置→图像→硬件视频解码）。**刷屏两源**：①解不了的 .mp4 持续解码重试 ②转码失败时 `createVideo` 直开原始 .mpg 兜底、老式容器同样每包失败。**本轮干净降级（不黑屏/不刷屏/不弹通知，解码真因待诊断）**：① **看门狗** `Video.FramesProcessed`（公开属性！）——附着视频过 1s 宽限仍 0 帧→`dropFaultedVideo`（dispose→停解码线程→**掐断刷屏**）→静态（`isUndecodableVideo`+`activeVideoAttachTime`）② **静态优先于黑**：`FramesProcessed==0` 期间显示静态、帧>0 才切视频（`applyActiveEntry` 视频态先 showFallback）③ **legacy 不裸开**：`createVideo` 对 `RequiresTranscode` 源转码不可用时回退静态、不再 `new Video(.mpg)` ④ 转码失败日志 Important→Verbose（不弹通知、去重保留）。**诊断待办**：①干净构建（**先关游戏再 build**，否则 osu.Desktop dll 被锁→relaunch 跑旧 dll，疑前几轮矛盾日志之因）②清 `bga-video-cache/` ③关“硬件视频解码”重放——播=硬解元凶（下一步强制软解，可能需全局 `FrameworkSetting.HardwareVideoDecoder` 在 BMS 游玩期 scoped 关闭）；仍静态=文件/demux 另寻。BMS 948/948。**教训**：别过早宣布转码 encode 是 decode 修复（baseline 假设也错了）；`Video.FramesProcessed` 是判定“开了但没解码”的可靠信号、可做看门狗掐刷屏。

**★真因确诊（前面 libx264/baseline/HW/demux 全是误判）＝并发转码写同一固定 temp 路径互相穿插污染、产出不可解码的 .mp4★**。用户给 `Error splitting the input into NAL units / Invalid NAL unit size (garbage > small)` + 提议查 ffmpeg。直接验证：①用户 `ffmpeg.exe`＝完整 gyan.dev 8.x（libavformat 62）含 libx264，**没问题**；②**用户自己的 ffmpeg 解不了缓存里的 .mp4**（`Invalid NAL unit size (0 > 25614)`）→文件本身坏；③同参数**全新转码一次→解码干净**（参数没问题）；④**模拟两 ffmpeg 并发写同一 temp→复现一模一样的 `Invalid NAL unit size (0 > 25614)`**（与缓存坏文件逐字节同错）。**根因**＝`startTranscode` 写固定 `<hash>.mp4.tmp`，转码 `Task.Run` 在 `BmsBgaPlayer` dispose 时**不取消**→用户退出/快速重放→新一局对**同一 temp** 起第二个 ffmpeg→字节交错→坏文件；一旦落缓存被 `Resolve` 的 `File.Exists` **永久端出**（解释了为何清缓存后偶发好、replay 后又坏、以及黑/静态/HW/SW 全一样——都是在解坏文件）。**修复**：①temp 加 `Guid`（`<hash>.<guid>.tmp`，并发各写各的永不穿插）②`inProgress` 改 **static**（跨 cache 实例去重，孤儿/重放不再起第二个 ffmpeg）③`File.Move(tmp,dest,overwrite:true)` 原子发布 ④`transcode_version`→3 失效旧坏缓存。**最大教训：缓存产物可能损坏且被 `File.Exists` 当成功端出，会把每一轮诊断引偏到解码端（白白试了 -f mp4/baseline/setpts/HW 诊断/看门狗）——遇“文件能开但解不了”先用产出它的同一 ffmpeg 解一遍验证文件本身，再怀疑解码器；以及任何“写 temp→改名”的缓存必须 temp 唯一 + 写入端去重，否则并发写必坏。** 干净降级（看门狗/静态优先/不裸开/Verbose）仍保留作兜底。**2026-06-22 用户确认老 `.mpg` BGA 可正常播放 ✅。**
