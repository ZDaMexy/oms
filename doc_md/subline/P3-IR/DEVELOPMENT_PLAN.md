# OMS IR 客户端与服务闭环计划

## 授权与范围

2026-10-03 用户授权“详细规划到闭环，然后按规划开工”。Phase 3 的独立 IR 本地开发提前开始，Phase 1.x 设备、皮肤与发行门继续保留。玩家主动启用后完成：注册 / 登录 → 游玩 → 最终结算与本地保存 → 交分 → 端内和网页查同一榜；断网或会话失效后恢复补交。关闭 IR 仍可完整离线游玩。

服务与网页在现有 `F:\zdamexy-workspace` 对应项目开发。跨端唯一合同位于 `oms-server/dev_bridge_md/doc_md/subline/oms-ir/constraints.md`，完整执行计划在同目录 `dev-plan.md`。本线维护客户端接入、用户数据与验收投影，不复制外部接口正文。osu-web 固定源码已取到该工作区，只参考页面组织、行为和边界，采用独立 FastAPI / SQLite 服务。

## 闭环顺序

| 门 | 玩家 / 维护者结果 | 退出条件 |
| --- | --- | --- |
| IR0 | 成绩身份和可比较条件明确 | 提交绑定源码、事实桥登记、合同与双方采用一致；BMS / PMS 9K、最终灯、血条、判定与计分版本不混淆 |
| IR1 | 本地真实账号、交分与网页试验榜 | 同局幂等、异内容冲突、账号隔离、分组榜、最佳分 / 最佳灯、服务重启、一致备份恢复和实际浏览器路径通过 |
| IR2 | 端内主动连接、保存后交分和查榜 | 默认 endpoint 空；Windows 凭据库存令牌；新局捕捉真实玩法条件；BMS / mania 正常保存后交分，不阻塞本地结算；端内 / 网页一致 |
| IR3 | 网络失败、重启及账号切换后补交 | 持久待交绑定服务与原账号；401 保全、重登续交；响应丢失重复无新增；匿名局不自动认领；关闭或本地删除不隐式删服务端历史 |
| IR4 | 50 人规模下可维护运行 | 真实主机与代表性数据量峰值预算、延迟 / 内存、备份恢复、账号恢复、滥用处理、TLS / 配置 / 留存与回退验收，再授权发布 |

各门独立验收，服务 fixture 不证明端内交分成功。50 人按每人约三分钟一局估算，平均约 0.278 次交分 / 秒，集中结束模型 50 局 / 10 秒；服务器约 500 MiB 新服务预算须实测。公网 100 Mbps 是峰值并按出网计费，不能代替 CPU、内存、磁盘与月费用预算。

## 下一道客户端门

1. 用独立 IR 设置、会话与按需 HTTP 消费者，不开启旧 IAPIProvider 在线总开关。
2. 只从真实新局的最终已保存 ScoreInfo 生成提交；持久 UUID 使用 ImportScore 回写的实际 ID，不挪用 OnlineID。
3. 捕捉可玩谱的实际 BMS KeymodeResolution / mania TotalColumns，原谱 MD5 / SHA256 沿既有验证来源；历史数字 9 不推断 PMS。
4. 最终 BMS v7 数据在 ruleset 的 PrepareScoreInfoForResults 之后才完整；交分必须在本地保存确认之后。初期只接正常完整保存的新局，失败 / 中退和历史回放导入另立需求。
5. 契约不支持的 Mod / 版本显示原因并保留待交；端内真实 Mod 消费者成立后逐项扩大，不用 Ranked 或本地 display bucket 作为公平榜准入。
6. Windows 凭据、待交归属与保存 / 退出竞态须用真实路径证明，再向主线回写能力。
