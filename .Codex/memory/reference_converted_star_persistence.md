The BMS→mania converted star-rating persistence chain (K9 subsystem, reviewed/hardened 2026-05-29):

**✅ 2026-06-23 — FIXED (K12): converted star WAS computed over a polluted object stream (now corrected).** `ManiaDifficultyCalculator.CreateDifficultyHitObjects` + `maxComboForObject` iterate `beatmap.HitObjects` with ZERO filter, but the BMS→mania converted beatmap's `HitObjects` still contains the BGM (`BmsConvertedBgmSampleHitObject`, Column 0) and scratch (`BmsConvertedScratchSampleHitObject`, anchor column) sample-only objects. `isScorableHitObject` only rewrites `TotalObjectCount`/`EndTimeObjectCount` (which the calculator NEVER reads) — it does NOT remove them from `HitObjects`, and mania has no `CreateBeatmapProcessor` override that strips ignore objects. So every BGM event (all dumped into column 0) + scratch sample feeds mania Strain/MaxCombo → **converted star is systematically inflated, magnitude scaling with BGM density** (keysound-heavy BMS often have BGM events ≥ playable notes → large inflation). ONLY pollutes star (display/sort/group); gameplay scoring is unaffected (IgnoreHit objects don't score). Root cause it stayed hidden: K9 #17 / K11 #3 / the test `TestScratchSamplesDoNotAffectConvertedDifficultyOrStoredCounts` all conflated "count-field exclusion" with "difficulty-input exclusion" — that test only asserts `TotalObjectCount` parity and NEVER runs `ManiaDifficultyCalculator`. Also: K11 (BGM emission, commit 9c97e48, 2026-06-01) changed the difficulty input but did NOT bump `conversion_version` (still 20260526) → pre/post-BGM stars can coexist inconsistently, both treated as current. **Fix (K12, LANDED 2026-06-23)**: new `ManiaDifficultyCalculator.isDifficultyRelevant(HitObject)` = `Judgement.MaxResult.AffectsCombo() || NestedHitObjects.Any(same)` (mirrors `ManiaAutoGenerator.canParticipateInAutoplay`; generic, no BMS ref) filters `CreateDifficultyHitObjects` (`beatmap.HitObjects.Where(isDifficultyRelevant).ToArray()`) AND `CreateDifficultyAttributes`'s `maxComboForObject` sum → keeps Note + nested-combo HoldNote, drops no-nested BGM/scratch. PROVABLY a NO-OP for native mania (only Note/HoldNote) so `ManiaDifficultyCalculator.Version` is intentionally NOT bumped (bumping → full native+converted library recompute at 5.7万 scale, wasteful + wrong for native). Instead bumped `current_bms_to_mania_conversion_version`→20260623 (invalidates ONLY BMS converted stars → `populateMissingConvertedStarRatings` recomputes the BMS library once on next startup, one progress notification). Tests now ACTUALLY run `Calculate()` over full-vs-scorable-filtered beatmaps via a `PreconvertedWorkingBeatmap` (overrides GetPlayableBeatmap to skip re-conversion, else the converter regenerates plain Notes and erases the sample-only objects). **pre-fix proof**: temporarily reverting the filter made the guards fail with scratch-dense star 0.817→1.742 (+113%) — quantifies the inflation. Verified: native `ManiaDifficultyCalculatorTest` 2/2 (pinned star unchanged), `BmsToManiaBeatmapConverterTest` 24/24, `BmsStarRatingResolverTest` 14/14, BMS 961/961, Release 0/0. Display & persistence layers were always SOUND — the bug was garbage-in at the calc layer only. Docs corrected across P1-K four-piece + mainline (2026-06-23). See [[reference-bms-keysound-chain]] (K11 BGM emission) and P1-K TECHNICAL_CONSTRAINTS K12. **Landmine for future maintainers: keep the #3/#4 asymmetry — do NOT bump mania Version (no-op for native), DO keep conversion_version current; and the regression test MUST run the real calculator, not assert TotalObjectCount.**

**2026-06-23 perf — `populateMissingConvertedStarRatings` batch reprocess parallelised** (the conversion_version bump above triggers a full-library recompute, and the user asked whether it could be sped up WITHOUT UI frame drops). Was single-threaded foreach + one realm write per beatmap. Now: chunk by 64, `Parallel.ForEach` the decode/convert/strain, one batched realm write per chunk. **Three invariants that keep it UI-safe (locked as P1-K TECHNICAL_CONSTRAINTS K10 #8 — do NOT break for more speed):** (1) degree = `Math.Clamp(Environment.ProcessorCount - 2, 1, 4)` — ALWAYS leaves the update+draw threads dedicated cores (using ProcessorCount directly would starve the UI → frame drops, the exact thing the user feared); (2) realm access stays on the ORCHESTRATOR thread only — workers do `GetWorkingBeatmap`+`Calculate`+`Invalidate`, ZERO realm (RealmAccess.Run/Write off the update thread uses a thread-local instance so it'd be *safe*, but funneling writes avoids scattering write contention across N threads); (3) batched writes (one txn/chunk) not per-item. Why confidently UI-safe even though it adds parallel compute: heavy decode runs OUTSIDE GetWorkingBeatmap's brief `lock(workingCache)` critical section; bounded degree leaves UI cores; batched writes reduce realm contention vs the old per-item loop; `sleepIfRequired()` kept in the worker body to yield to gameplay. Behaviourally equivalent per-item (same Failed classification, same persistence calls). Mirrors the already-shipped, user-verified `BmsChartFilterStatsBackfill` (degree-2 parallel + direct-bms-bypass; 910/910·922/922). NOTE the architectural constraint: this path is in osu.Game which CANNOT reference BMS types, so it must use the generic `GetWorkingBeatmap` (can't do the direct-.bms-decode bypass the backfill uses, which lives in the BMS assembly) — the bypass would need moving the reprocess into a BMS-side OnSongSelectSetup backfill. No headless integration test for this path (OsuGameTestScene-level, CLI-discovery-flaky) — validated by build + behavioural equivalence + reasoning.

**2026-05-29 hardening — invariants now enforced by code, not just docs**:

- **`BmsToManiaBeatmapConverter.ConvertBeatmap` throws `BeatmapInvalidForRulesetException`** when flatten produces zero scorable mania objects (scratch-only or empty source). K9 #9 was previously doc-only; the converter now enforces it. Both lazy (`BeatmapDifficultyCache.computeDifficulty`) and batch (`BackgroundDataStoreProcessor.populateMissingConvertedStarRatings`) catches already persist this as Failed.
- **STOP-freeze uses dedicated `BmsStopFreezeTimingControlPoint : TimingControlPoint` subclass**, not a `BeatLength = 6` sentinel. Mania `TimingControlPoint.BeatLengthBindable.MinValue = 6` means any BPM ≥ 10000 real chart clamps to `BeatLength = 6` and would collide with a value-tagged sentinel. K9 #16 (new) requires type-level marking; `isBmsStopFreezeTimingPoint` is now `timingPoint is BmsStopFreezeTimingControlPoint`.
- **mania conversion drops BMS `EffectControlPoint`** (`SCROLLxx/SC` scroll-speed events written by BMS converter). K9 #15 (new) declares this is intentional — BMS scroll is engine-specific visual semantics, not mania SV. Don't try to "fix" the missing scroll in mania view without a new K-slice.
- **`BmsToManiaBeatmapConverter.createSourceBeatmap` reuses K5 cache**: queries `BmsDecodedBeatmap.TryGetCachedModlessPlayableBeatmap("bms", ...)` first; writes back via `CacheModlessPlayableBeatmap` after first conversion. Eliminates double BMS→BMS conversion when both BMS playable and mania playable are requested from the same source.
- **`BmsPersistedMetadataResolver.parsedDataCache` evicts on write**: `setConvertedStarRating` calls `TryRemove(previousJson, ...)` after writing the new payload so cache occupancy stays bounded to 1 entry per beatmap (was previously unbounded under mutation cycles).
- **`BeatmapDifficultyCache.persistConvertedStarRatingIfApplicable` guards with `!metadata.IsManaged`**: detached metadata gets the in-memory write (for live bindable updates), live realm instances are written exclusively via `realmAccess.Write`. Calling either method with a managed metadata outside a write transaction no longer throws RealmException.
- **`ManiaRuleset.tryCreateBmsConverter` uses cached reflection delegates** (`static readonly Func<IBeatmap, bool>?` + `static readonly Func<IBeatmap, Ruleset, IBeatmapConverter>?` via `Delegate.CreateDelegate`), mirroring `DrawableManiaRuleset`'s existing pattern. Eliminates per-CreateBeatmapConverter `Type.GetType` + `GetMethod` + `Invoke` overhead at 58k+ library scale.

**2026-06-10 perf — the converter no longer computes the mania star itself** (P1-K K9 #17, perf review of 转谱链路): `BmsToManiaBeatmapConverter.ConvertBeatmap` used to run a FULL `ManiaDifficultyCalculator` pass at its tail and write the result into `convertedBeatmap.BeatmapInfo.StarRating` (the now-deleted line 77 + `createDifficultyBeatmap` helper). That value was redundant on EVERY path: the persistence path (`computeDifficulty` / `BackgroundDataStoreProcessor` / import-time `EnsureConvertedStarRatingPersisted`) re-runs `ManiaDifficultyCalculator.Calculate()` over the same playable right after `GetPlayableBeatmap` and persists THAT — so the converter's pass was a wasted 2nd strain calc (doubles converted-star reprocessing at 5.7万 scale); the gameplay load path doesn't read the playable's StarRating at all (uses persisted/DB). Removed; star ownership is solely `ManiaDifficultyCalculator`/`BeatmapDifficultyCache`, matching upstream `ManiaBeatmapConverter` (sets no star). **Landmine: do NOT re-add a star computation inside the converter** — it's pure redundant CPU. After removal the converted beatmap's `BeatmapInfo.StarRating` carries the BMS playlevel (from `populateMetadata`), which is never consumed downstream. Guard: `BmsToManiaBeatmapConverterTest` no longer asserts converter-side star (removed `TestConvertedBeatmapStarRatingUsesManiaDifficultyCalculator`; 19→18). Persistence behaviour unchanged.



**Storage**: `BeatmapMetadata.RulesetDataJson` (Realm col `RulesetData`) holds `BmsPersistedMetadataData` = `{ chart_metadata, converted_star_ratings: { "mania": { star_rating, difficulty_version, conversion_version, failed } } }`. Writers must round-trip via `getPersistedData() ?? new()` so `chart_metadata` is preserved. All accessed through `BmsPersistedMetadataResolver` (internal) + `BmsStarRatingResolver` (public).

**Dual-version invalidation** (a read is valid only if BOTH match):
- `conversion_version` — manual const in `BmsPersistedMetadataResolver` (date int, e.g. 20260526). Bump on any converter logic change.
- `difficulty_version` — mania `DifficultyCalculator.Version`; read requires `== RulesetInfo.LastAppliedDifficultyVersion`. That LAV is persisted to realm by `BackgroundDataStoreProcessor.clearOutdatedStarRatings` (runs early in LoadComplete); `populateMissingConvertedStarRatings`'s LAV assignment is in-memory-only and depends on that.

**Write paths** (in order of when they fire):
1. **Import-time** (added 2026-05-28, K10-A): `BeatmapUpdater.Process()` calls `BeatmapDifficultyCache.EnsureConvertedStarRatingPersisted(beatmapInfo, working)` for BMS beatmaps inside the existing realm write transaction. Writes directly to live metadata (no nested write). Best-effort: any exception is logged/swallowed so import never fails. Mirrors how native star is computed during import → bulk imports are mania-ready without restart.
2. Lazy: `BeatmapDifficultyCache.computeDifficulty` → `persistConvertedStarRatingIfApplicable` (gate: IsBms + target mania + no mods). Writes both detached metadata and live realm beatmap.
3. Batch (fallback): `BackgroundDataStoreProcessor.populateMissingConvertedStarRatings` at startup, for BMS beatmaps lacking current state (existing library that pre-dates import-time persist, or version invalidation).

**Read path**: `BmsStarRatingResolver.TryResolvePersistedConvertedStarRating` → consumers: `tryGetImmediateDifficulty` (fast display), `PanelBeatmapSet/Standalone.SpreadDisplay`, `BeatmapCarousel` selectors via `RequiresRulesetSpecificStarRating`.

**Failure semantics** (unified 2026-05-28): only `BeatmapInvalidForRulesetException` (deterministic non-convertibility) persists `failed=true` (sticky until a version bump — `HasCurrentConvertedStarRatingState` treats Failed as "current"). Transient errors (IO etc.) are logged only, NOT persisted, so they retry next run. Both the cache lazy path (`persistConvertedStarRatingFailureIfApplicable`) and the batch path follow this.

**Why the read gate "looks fragile" but isn't in practice** (K10-B deferral, 2026-05-28): the `DifficultyVersion == localRuleset.LastAppliedDifficultyVersion` check depends on the consumer-passed ruleset's LAV. But all consumers (carousel `FilterCriteria.Ruleset`, spread display `ruleset.Value`, difficulty cache `currentRuleset`) share the same `RulesetStore.AvailableRulesets` detached instance — global `Ruleset.Value` is set from `RulesetStore.GetRuleset/First` — and `clearOutdatedStarRatings` synchronises that instance's LAV on every startup (realm-persisted after first bump). `ManiaDifficultyCalculator.Version` is a compile-time constant. So the gate is reliable in steady state. K10-B (decouple read from consumer LAV) was investigated and deferred — not needed in practice. Revisit only if a real consumer holding a stale-LAV ruleset is found.

**Critical landmines learned from 58k+ BMS library testing (K10 second slice, 2026-05-28)**:

1. **Realm 20.1.0 link-traversal predicate translation is unreliable**: `r.All<BeatmapInfo>().Where(b => b.Ruleset.ShortName == "bms")` silently returned zero matches against a real 58k-beatmap library — no exception, no fallback to client-side eval, just empty. Always filter `Where(b => b.BeatmapSet != null)` server-side and apply `BmsStarRatingResolver.IsBmsBeatmap(b)` client-side. Same pattern used in `BmsChartFilterStatsBackfill.cs` and `BmsDifficultyTableManager.cs` uses `.ToList()` to force materialisation — those might also be at risk but haven't been verified.

2. **`DifficultyCalculator.Calculate()` has a built-in 10-second timeout (upstream)**: when called without a `CancellationToken` (or with `CancellationToken.None`), it substitutes its own `CancellationTokenSource(TimeSpan.FromSeconds(10))`. Charts that take >10s to convert (large BMS with pathological measure/event patterns) throw `OperationCanceledException` *every* call. For BMS→mania persistence paths that don't pass a token (batch reprocess + K10-A import-time persist), this OCE is **deterministic per beatmap** — treat as Failed, not transient. Otherwise every startup wastes 10-25s and every carousel filter requiring star lookup blocks on the same async compute.

3. **`MemoryCachingComponent.CacheNullValues => false` for BeatmapDifficultyCache**: failed `computeDifficulty` returns (null result) are NOT cached. Every subsequent lookup re-runs the slow compute. Workaround is at the read layer, not the cache: `tryGetImmediateDifficulty` must synchronously return a fallback (`StarDifficulty(beatmapInfo.StarRating, ...)` using BMS playlevel) whenever `BmsPersistedMetadataResolver.HasCurrentConvertedStarRatingState` is true — *including* the Failed sub-state — so the carousel never queues an async compute for known-failing beatmaps.

4. **Per-beatmap async lambda allocation is the dominant cost at 57k scale**: `Task.WhenAll(beatmaps.Select(async b => await GetDifficultyAsync(b)))` over 57k items allocates 57k async state machines + 57k `Task<>` instances even when every `GetDifficultyAsync` returns synchronously via `Task.FromResult`. Sync-first split is essential: iterate with `TryGetCachedDifficulty` (sync), collect misses into a side list, only `Task.WhenAll` the misses. For a fully persisted library this means zero Task allocations.

**Write paths** (in order of when they fire, post-K10 second slice):
1. **Import-time**: `BeatmapUpdater.Process()` calls `BeatmapDifficultyCache.EnsureConvertedStarRatingPersisted(beatmapInfo, working)` inside the existing realm write transaction. OCE catch persists Failed (since no token passed → guaranteed internal-timeout source).
2. Lazy: `BeatmapDifficultyCache.computeDifficulty` → `persistConvertedStarRatingIfApplicable`. Carousel async path; OCE here may come from user cancellation, so NOT classified as Failed.
3. Batch (fallback): `BackgroundDataStoreProcessor.populateMissingConvertedStarRatings` at startup. OCE catch persists Failed (same rationale as path 1).

**Read path** (post-K10 second slice):
- `tryGetImmediateDifficulty` (sync) returns `true` for: persisted-Success → real star; persisted-Failed → fallback to BMS playlevel; non-persisted → returns false, falls through to cache.
- `TryGetCachedDifficulty` (sync) → immediate first, then `CheckExists` in MemoryCachingComponent.
- `GetDifficultyAsync` (async) → immediate first, then `GetAsync` which queues compute via single-thread `updateScheduler`.
- `BeatmapCarousel.getEffectiveStarRatingsStrict` is sync-first: iterate `TryGetCachedDifficulty`, only async-await the misses.

**Known by-design gaps**: immediate-display MaxCombo uses BMS source combo (cosmetic). Resolver-level Failed contract is locked by `BmsStarRatingResolverTest`; the BeatmapUpdater import-time persist & cache/batch "stick vs retry" end-to-end regression is still a test gap (OsuGameTestScene-level, blocked by CLI discovery flakiness on visual scenes). UI-side: high-difficulty star sprite-text shows a "counting" animation on carousel panels — that's a panel display layer concern (P1-A territory), not a data-layer issue.
